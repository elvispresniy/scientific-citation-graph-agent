# Gumbel-Top-k: C++17 / OpenMP

Параллельное ядро первого шага фабрики. На входе уже допущенные кандидаты и
положительные веса. Подготовка графовых метрик, HTTP, полнотексты и LLM в ядро
не входят. Исторический `random.randrange` в `graph_pilot` сохранён.

## Алгоритм и воспроизводимость

Для каждой пары `(uint64 ID, weight)` независимо рассчитывается
`score = log(weight) - log(-log(U))`. Выбираются K наибольших score; при равенстве
первым идёт меньший числовой ID. Каждый поток хранит локальные лучшие K в куче,
затем списки объединяются в глобальную кучу и сортируются по score. Кандидат вне
локальных лучших K не может войти в глобальные лучшие K.

Локальный отбор: O(N log K) в общем случае (при K=1 — O(N)); объединение:
O(P K log K); сортировка: O(K log K). Дополнительная память отбора:
O(min(N, P K)); загруженные входы: O(N). Объединение пока последовательное.

В модели независимых непрерывных U получается распределение последовательных
извлечений пропорционально оставшимся весам:
[Kool et al., ICML 2019](https://proceedings.mlr.press/v97/kool19a.html).
Программа использует конечную точность и псевдослучайные числа. Выбранные ID
не обязаны совпадать с историческим MT19937/randrange при том же seed.

U получается из `SplitMix64(id XOR SplitMix64(seed))`; берутся середины 52-битных
интервалов, чтобы исключить U=0 и U=1. Ключ не зависит от порядка строк или числа
потоков. Версия RNG: `gumbel-topk-splitmix64-v1`. Побитовое совпадение score
проверяется для одного бинарного файла и машины; между libm/компиляторами возможны
различия округления. Флаг `-ffast-math` не используется.

## Сборка

Перед работой на Ломоносове-2 прочитать
[памятку доступа и сохранённые правила](../../research/lomonosov2-access/README.md).
Вычислительные запуски выполняются через SLURM из `_scratch`.

Linux / GCC, включая перенос на кластер:

```sh
make -C code/gumbel_topk CXX=g++
```

macOS / Apple Clang требует `libomp`:

```sh
brew install libomp
make -C code/gumbel_topk CXX=clang++
```

Флаги по умолчанию: `-O3 -std=c++17 -Wall -Wextra -Wpedantic`, плюс OpenMP.
`make -C code/gumbel_topk serial` собирает отдельный бинарный файл без OpenMP,
который отклоняет `--threads > 1`. Основной бинарный файл с `--threads 1` — база
для сравнения на том же языке, с теми же структурами и RNG. Сборка записывает
SHA-256 C++-исходника в бинарный файл. Для курса сохраняйте команду сборки,
настройки привязки потоков и сведения об аппаратуре.

## Запуск по существующему снимку

```sh
PYTHONPATH=code python3 -m graph_pilot \
  --db research/unarxive-pilot/graph.sqlite factory-step1 \
  --config code/graph_pilot/configs/factory-step1-local.json \
  --sampler gumbel-native --threads 4 --repeat 7 \
  --output research/factory-step1-pilot/run-gumbel-001
```

Каталог должен быть новым. Используется неизменённый `analyze` старого пилота:
тот же допуск, степени, доступность и отпечатки входов. SQLite открывается только
для чтения. Конфигурация фабрики пока допускает только одинаковые веса;
произвольные веса в ядре не означают готовое обогащение площадками.

Адаптер переводит paper_id в первые 64 бита SHA-256 (little-endian), проверяет
коллизии и пишет `eligible.tsv`. Seed нормализуется по модулю 2^64. Результаты:
config/candidates/selected/report, score, времена подготовки и ядра, версии,
хеши бинарного файла и входа. Ошибка оставляет незавершённый каталог: проверяйте
наличие `report.json` и выбирайте новый каталог для повторного запуска.

Отдельный интерфейс ядра, TSV без заголовка: уникальный числовой ID и вес:

```sh
code/gumbel_topk/build/gumbel_topk \
  --input eligible.tsv --k 20 --seed 42 --threads 4 --repeat 7 --warmup 1
```

Пустой пул, K=0 и K>N поддерживаются. Возвращаются min(K,N) статей. Нулевые,
отрицательные, нечисловые и бесконечные веса, повторные ID отклоняются.

## Проверка и измерения

```sh
make -C code/gumbel_topk all serial
PYTHONPATH=code python3 -m pytest -q code/graph_pilot/tests
python3 code/gumbel_topk/benchmark.py \
  --output research/factory-step1-pilot/scaling-gumbel-001 \
  --sizes 100000 1000000 10000000 --threads 1 2 4 8 --repeat 7 --warmup 1
```

Тесты сравнивают C++ с независимым полным сортированием всех score в Python,
проверяют веса, крайние случаи, идентичность ID и score для 1/2/4/8 потоков,
перестановку строк, запрет повторов и неизменность SQLite. Без собранного ядра
нативные тесты пропускаются; неверный явный GUMBEL_BINARY — ошибка.

Бенчмарк использует **синтетические** ID 0..N-1 и веса 1 либо явно заданный
`--weight-pattern skewed`: 10^(id%7-3). Это исследование ядра, а не новые реальные
статьи и не оценка качества научных задач. Для каждого размера фиксированы N, K,
seed, веса и все вычисления; меняется P. Повторения используют те же ключи.
Сохраняются сырые времена и медианы, ускорение T(1)/T(P), эффективность,
точное совпадение с одним потоком и окружение.

Ядро измеряется без генерации/чтения входов и запуска процесса. Включены ключи,
локальный отбор, объединение, сортировка и временные выделения памяти этих фаз.
Подготовка графа измеряется отдельно адаптером и не объявляется ускоренной.
На 648 реальных кандидатах накладные расходы OpenMP могут превышать выигрыш.
Локальные результаты не заменяют запуски на «Ломоносове-2».

## Кластерная матрица

Подготовлены [инструкции и скрипты SLURM](cluster/README.md) для GCC 12.3.0 и
Python 3.6+, одного узла `test`, P=1/2/4/8/14. Пример полной матрицы локально
(число потоков выбирать по доступным ядрам):

```sh
python3 code/gumbel_topk/benchmark.py --output /tmp/gtopk-new-matrix \
  --sizes 100000 1000000 10000000 100000000 --k 20 1000 10000 \
  --weight-pattern uniform skewed --threads 1 2 4 8 --repeat 7 --warmup 1
```

Для каждого N/K/распределения используется отдельная однопоточная база.
Отчёты включают все измерения и параметры входа, привязку CPU и идентификатор
SLURM. Метка `lomonosov2` разрешена только внутри задания SLURM; локальные
измерения сохраняют метку `local`. Генератор входа уже встроен в C++-ядро,
синтетический граф и большой файл входов не требуются.
