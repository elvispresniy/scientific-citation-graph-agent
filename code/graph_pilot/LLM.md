# LLM для будущего шага 1.5

`llm.py` подключает предоставленный пользователем OpenAI-совместимый сервер через
Python SDK. Это адаптер транспорта и команда проверки подключения, а не реализация
содержательного фильтра шага 1.5. Алгоритм фильтра пока не определён.

Установка дополнительной зависимости:

```sh
python3 -m pip install -r code/graph_pilot/requirements-llm.txt
```

Ключ не хранится в конфигурации или исходниках. Доступны `GRAPH_LLM_API_KEY`
в окружении процесса либо скрытый ввод с `--ask-key`. Значение `OPENAI_API_KEY`
автоматически не подхватывается: ключ для другого сервиса нельзя отправлять на этот
сервер по ошибке. Используется предоставленный HTTP-адрес, без TLS.

Из корня репозитория:

```sh
PYTHONPATH=code python3 -m graph_pilot.llm models --ask-key

PYTHONPATH=code python3 -m graph_pilot.llm smoke \
  --ask-key \
  --output /tmp/graph-llm-smoke.json
```

Пользователь выбрал `qwen38_27b` для шага 1.5; ID сохранён в конфигурации
`configs/llm-server.json` без секретов. Параметр `--model` явно переопределяет этот выбор
для конкретного запуска. Серверный список моделей не служит рейтингом качества.

По умолчанию: таймаут запроса 20 секунд, максимум 2 вызова на экземпляр клиента,
не более 20 000 символов входа и 128 выходных токенов на генерацию. Вызовы идут
последовательно. SDK настроен с `max_retries=0`; после 429, ошибки сервера или
таймаута клиент останавливается. Перехода к другому серверу или модели нет.
Конфигурацию SDK сверяли с [официальной документацией](https://developers.openai.com/api/reference/python),
фактически проверенная локальная версия `openai` — 2.21.0.

Лимит 128 токенов относится к дешёвой проверке подключения; это не согласованный
бюджет содержательной пробы шага 1.5. Команда `smoke` посылает только короткую
служебную просьбу вернуть `{"ok":true}`. Статьи она не читает и не отправляет.
Выходной JSON фиксирует модель, лимит, usage и finish_reason, но не ключ.
Существующий файл результата не перезаписывается.

Если HTTP-запрос выполнился, но ответ пуст, обрезан или не соответствует контрольному
JSON, в отчёте будет `http_completion_received=true`, `ok=false`, код завершения 1.
Это не ошибка доступа, но и не успешная проверка готового ответа. Автоматического
увеличения бюджета и повторного запроса нет. Проверка JSON здесь относится только
к контрольной строке, не устанавливает поддержку JSON Schema / Structured Outputs.

В программном использовании `LLMClient.complete(model, messages)` возвращает текст,
модель, finish_reason и usage. Вызывающий шаг обязан проверить завершённость ответа
и собственную схему результата; обрезанный ответ нельзя принимать за научное решение.

Рабочая модель выбрана; бюджет и формат научных свидетельств для шага 1.5 ещё нужно задать.
В частности, необходимо определить, какие соседи читаются и что считается основанием
передать окружение на шаг 2. Этот адаптер таких решений не принимает.
