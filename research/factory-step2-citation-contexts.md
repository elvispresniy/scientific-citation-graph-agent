# Шаг 2: хранение контекстов и связи кандидатов

25 октября 2026. По вопросу пользователя описан конкретный технический вариант.
Различаем существующее хранение и предложение исполнителя; вопрос не считается
утверждением новой схемы или поручением реализовать API/очередь.

## Уже существующее хранение

В локальной SQLite есть таблица:

```sql
edges(
    src TEXT REFERENCES papers(id),
    dst TEXT REFERENCES papers(id),
    influential INTEGER,
    evidence TEXT,
    PRIMARY KEY (src, dst)
)
```

`src` цитирует `dst`; `evidence` — сериализованный JSON. В нём уже есть
`contexts`, список окон текста из цитирующей работы. Упрощённая иллюстрация
формата (A и B — условные ID, текст является заполнителем):

```json
{
  "src": "A",
  "dst": "B",
  "evidence": {
    "source": "unarxive_bibliography",
    "bib_key": "ref17",
    "contexts": [
      {"section": "Methods", "text": "Текст вокруг ссылки на B в статье A"}
    ]
  }
}
```

В фактическом context также есть `start`, `end`, `window_start`. Это детали
извлечения, не поля карточки. Импорт сохраняет до двух контекстов для
библиографической записи; это не все упоминания и не обязательно полные
предложения. Пустой contexts не означает отсутствие ребра или нерелевантность.
Read-only проверка реальной записи подтвердила эти поля; БД не менялась.

## Предложенная структура границы

На первый вариант предлагается переиспользовать edges/evidence. Контексты
остаются свойством ребра, карточки — свойством допущенной статьи. Для кандидата
храним ID и ключи связывающих рёбер. Если допущенные A и C цитируют новую B:

```json
{
  "paper_id": "B",
  "connections": [
    {"src": "A", "dst": "B"},
    {"src": "C", "dst": "B"}
  ]
}
```

Пара `(src,dst)` — существующий первичный ключ. По ней читаем contexts из БД;
для ранжирования можно собрать connections уже с этими текстами. Это производный
рабочий пакет, а не вторая независимая копия графа. У B одна запись независимо
от числа путей обнаружения; новое основание добавляется к connections.
По ID получаем метаданные/текст статьи и связываем с карточкой после допуска.
Отказ и допуск исключают повторный выбор ID в данном проходе.

## Направления и получение данных

- Исходящие рёбра `src=A` дают references известной A. При A→B контекст в A.
- Входящие `dst=A` дают citations. При B→A контекст в B; в локальном снимке
  он заранее извлечён без нейросети. Этот текст нельзя приписывать статье A.
- Оба конца уже допущены — нового кандидата нет. Сосед ранее отклонён —
  повторная связь не возвращает его в очередь. Политика открытия ещё не
  исследованных ветвей здесь не выбирается.

Первичный ключ обслуживает исходящие переходы, индекс edges_dst — входящие.
Читаем рёбра, инцидентные нужному набору ID, декодируем evidence и группируем
по соседнему ID. Сборка не требует передавать модели полнотексты всех соседей.

Число контекстов не равно числу цитирующих статей. Локальная цитируемость B —
число уникальных src при dst=B; связи с допущенным набором считаются отдельно.
Контекст объясняет происхождение ссылки, но не создаёт автоматически
семантическую связь и не доказывает общности научного содержания.

## Что ещё не сделано

Текущие методы/маршруты neighbors contexts не возвращают. Требуются внутреннее
чтение рёбер с evidence и сборка границы/пакета ранжирования. В этой итерации
код и публичный API не меняются. Повторно импортировать корпус ради уже
сохранённых контекстов не нужно. Метод оценки контекстов и функция приоритета
кандидата не выбраны.

Основание предложения — существующая схема, сохранение происхождения и
направления и устранение дубликатов. Польза для выбора остаётся гипотезой.

## Предложение численного критерия — 25 октября 2026

Статус: вариант ассистента для обсуждения, не согласован и не реализован.
Предварительное ранжирование не заменяет содержательный допуск по полнотексту.

Разделяем два признака. Структурная поддержка `support(p)` — количество
различных допущенных статей, соединённых с кандидатом p хотя бы одним ребром
в любом направлении. Повторения ссылки и число сохранённых окон не увеличивают
support; глобальная цитируемость — другой показатель.

Содержательный признак `context_score(p)` можно получить без нового LLM-вызова:
взять сохранённые контексты рёбер между p и допущенным набором; собрать для
каждого аспекта накопленных карточек текст из problem, mechanism_or_approach,
conventional_terms.term и meaning; преобразовать окна и описания аспектов
одним индексом TF-IDF либо обсуждавшимся TF-IDF+LSA. Затем посчитать косинус
между каждым окном и каждым аспектом. Предложение базовой агрегации:
`context_score(p) = max cosine(context_vector, aspect_vector)`.
Сохранять также ребро и аспект, давшие максимум. Сам индекс пока не построен,
вариант представления, его параметры и способ совместить признаки не выбраны.

Мотив максимума — не требовать нескольких связей от потенциальной связующей
работы; это инженерный базовый вариант, а не проверенный лучший агрегатор.
Он чувствителен к случайному высокому совпадению и количеству окон. Отсутствие
контекстов или представимого словаря означает неизвестное значение, не отказ.
Косинус не является вероятностью; для LSA он может быть отрицательным.

Особое ограничение: при A→p окно написано в A и может совпадать с карточкой A
потому, что описывает собственную работу A. Даже высокое совпадение не доказывает,
что p развивает этот аспект; ссылка может быть фоновой, групповой или критической.
При p→A окно происходит из p, но и там требуется проверка роли ссылки.
Поэтому предложение оценивает перспективность перехода, не научную близость
кандидата как установленный факт. Веса, порог и tie-breaker не утверждаются.

Проверка гипотезы: при одинаковом бюджете чтения сравнить случайный порядок,
support и context_score по доле содержательных допусков и обнаружению связующих
работ; дополнительно проверить зависимость от числа окон. Эксперимент не запущен.
