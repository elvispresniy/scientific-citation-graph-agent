## 1. PaSa: прямое обоснование сохранения промежуточных статей

Источник: [PaSa, arXiv:2501.10120v2](https://arxiv.org/html/2501.10120v2), §4.1–4.3, Figure 2, §5.1–5.2.

**Утверждения статьи.** Crawler отвечает за полноту поиска, Selector — за точность конечного отбора. Figure 2 прямо описывает полезное исследование через промежуточные статьи, не соответствующие запросу: “even when intermediate papers along the path do not align with the user query.” Expand выбирает подраздел и добавляет его ссылки в очередь. Stop завершает текущую сессию, переключая контекст на запрос и следующую статью; это не остановка всего поиска. При обучении формула (3) учитывает ожидаемую будущую ценность добавленных статей наряду с немедленной наградой и затратами. Это основание для навигационной полезности без собственной финальной релевантности. В экспериментах глубина ограничена тремя. Статьи сохраняются в БД; отсутствующие получаются через ar5iv.

**Официальная реализация — отдельный уровень доказательства.** Проверен HEAD main через `git ls-remote`: commit `2aaa6a9b1e48d24a2b7e21e8551f863dad9eeb84`; `paper_agent.py` дополнительно получен по этому SHA и строки пересчитаны по raw-файлу. Это зафиксированная текущая реализация; её тождество версии экспериментального runner статьи не установлено. В [paper_agent.py](https://github.com/bytedance/pasa/blob/2aaa6a9b1e48d24a2b7e21e8551f863dad9eeb84/paper_agent.py#L80-L115) условие score > 0.5 добавляет название только в конечный `recall_papers`. Независимо от него каждая новая статья добавляется в `papers_queue` (строки 97–115 и 184–205). Следовательно, отрицательное решение Selector не запрещает дальнейшее раскрытие статьи. Однако [expand, строки 207–221](https://github.com/bytedance/pasa/blob/2aaa6a9b1e48d24a2b7e21e8551f863dad9eeb84/paper_agent.py#L207-L221) сортирует свежую часть очереди по тому же `select_score`; на глубинах >0 берёт только `expand_papers` лучших. На первом слое все найденные статьи допускаются к выбору подразделов (при доступном содержимом); на последующих — только top20 при значении по умолчанию. Это не означает, что все статьи раскрываются: Crawler ещё должен выбрать подразделы. Кроме того, `expand_start` продвигается за всю свежую очередь, поэтому не попавшие в top20 не остаются отложенным фронтом для следующих слоёв. Значит, runner сохраняет низко оценённые статьи в истории, но может навсегда пропустить их раскрытие из-за лимита. Параметры по умолчанию: 2 слоя раскрытия, 20 раскрываемых работ на последующих слоях. Это не идентично ограничению глубины в статье.

Память: [paper_node.py](https://github.com/bytedance/pasa/blob/2aaa6a9b1e48d24a2b7e21e8551f863dad9eeb84/paper_node.py) хранит ID, глубину, происхождение, аннотацию, подразделы со ссылками, оценку, дочерние узлы. `touch_ids` в агенте исключает повторную обработку; дерево сохраняет путь обнаружения. Отдельной общей памяти научных гипотез здесь не показано.

В [agent_prompt.json](https://github.com/bytedance/pasa/blob/2aaa6a9b1e48d24a2b7e21e8551f863dad9eeb84/agent_prompt.json) выбор подраздела формулируется через вероятность найти больше нужных статей; финальный отбор отдельно спрашивает соответствие самой статьи запросу. Это два разных вопроса, хотя ранжирование очереди в runner использует relevance score.

## 2. PaperPilot: расширение и отбор как разные операторы

Источник: [Multi-Turn Agentic Scientific Literature Search via Workflow Induction, arXiv:2607.00597v2](https://arxiv.org/html/2607.00597v2), §2.1–2.2, приложения A.1–A.2, C.3.

**Утверждения статьи.** При заданных anchor paper и query система строит DAG типизированных операций. `citation_expand(papers, direction, max)` отделён от `filter`, `score`, `top_k`, `llm_rerank`, `nli_filter`, `fine_read`. Промежуточные результаты кэшируются и могут переиспользоваться. Состояние включает запрос, затравку, текущий набор и историю взаимодействия; пользовательская обратная связь меняет структуру DAG и параметры.

**Чего источник не устанавливает.** Отдельной функции ценности промежуточного моста или обязательного правила продолжать через нерелевантную работу в прочитанных разделах нет. Архитектура позволяет раскрыть множество до финального фильтра, но сама по себе не гарантирует сохранения мостов. Результаты ориентированы на известный пользовательский запрос. Приложение C.3 описывает уточнения до 4–5 ходов, затем единственный retrieval pass с обогащённым запросом; нельзя приписывать всей оценке неограниченный циклический поиск с обратной связью после каждого прочтения.

[Официальный README](https://github.com/mtilyxuegao/PaperPilot) дополнительно сообщает о сохранении DAG, его изменений, времени операций, расходов и финального списка. Подробный runtime-код PaperPilot в этой проверке не прочитан. Ссылка README на `docs/architecture.md` при проверке raw URL вернула 404.

## 3. SPAR: полезный контраст, но не решение проблемы мостов

Источник: [SPAR, arXiv:2507.15245v1](https://arxiv.org/html/2507.15245v1), §3.2, §6.2, Limitations.

**Утверждения статьи.** Judgement Agent сначала оценивает соответствие исходному запросу по метаданным. Только прошедшие relevance threshold работы входят в Related Pool; именно их ссылки раскрывает RefChain. Ссылки проходят ту же оценку. RefChain ограничен одним слоем, без рекурсивного раскрытия ссылок найденных ссылок в этом цикле. Лучшие K работ сохраняются в Paper Cache. Для них генерируются новые запросы по методам, применениям и ограничениям; случайная часть запросов идёт в следующую итерацию. Учитывается история, отсекаются повторные запросы и пересечения ключевых слов. Остановка — размер кэша или максимальная глубина. Авторы прямо признают, что один слой может упускать глубоко расположенные релевантные работы.

**Вывод по алгоритму.** Это пример управляемой стоимости, а не защита низкорелевантного моста: работа, не прошедшая начальный порог, не получает раскрытия RefChain по описанному правилу. Публичный код SPAR в этой проверке не прочитан; точные значения порогов/лимитов не установлены.

## 4. Что переносится в нашу фабрику: выводы субагента

Ниже предложения, а не результаты статей и не принятые решения проекта.

1. **Разделить два решения:** подходит ли статья в будущий набор целей; стоит ли исследовать её связи. Отказ по первому не должен автоматически закрывать второе. PaSa даёт наиболее прямое основание для этого разделения.
2. **Хранить все рассмотренные статьи с происхождением и независимыми статусами**, а не только прошедшие содержательный фильтр. Нужны основания решения и возможность вернуться, когда накопленный набор изменится. Первая часть имеет аналог в очереди/дереве PaSa; возвращение после изменения гипотез — наше расширение.
3. **Не выдавать top relevance за оценку навигационной полезности.** Именно чтение кода PaSa показывает остаточный риск: низкий relevance score может вытеснить мост при ограничении очереди. Предложение для обсуждения — отдельный резерв исследования, а не безлимитное сохранение всех ветвей.
4. **Навигационный потенциал можно оценивать до чтения всех соседей:** по структуре ссылок, подразделам и контекстам цитирования. PaSa выбирает подразделы с ожидаемыми полезными ссылками; перенос к входящим ссылкам или нашему накопленному набору потребует собственной проверки.
5. **Модульность можно реализовать явным порядком операций:** расширение, содержательная оценка, ограничение очереди, финальный отбор. PaperPilot полезен этим инженерным разделением, но не даёт готовой функции мостовой ценности.

Ключевое ограничение переноса: все три системы решают поиск относительно уже заданного запроса. У фабрики окончательный общий аспект появляется позднее. Поэтому нельзя просто заменить название Selector и считать вопрос отбора решённым: полезность нужно определять относительно развивающегося набора и нескольких предварительных направлений. Доказательств, что какая-либо из трёх систем уже решает именно эту постановку, в проверенных материалах нет.
