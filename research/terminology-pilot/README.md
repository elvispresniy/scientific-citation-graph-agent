# Пилот: словарь вопросов и целевых статей

Зафиксировано с пользователем 11 октября 2026 года. Текущий этап сравнивает **совпадение научного словаря вопроса и целевой статьи** при разных правилах совпадения и разных частях текста. Поисковые системы не запускаются.

Основной результат — [читаемый отчёт с полной сеткой показателей](metric-comparison.md). [Подробное приложение](term-match-details.md) содержит оригинальные вопросы, все цели и списки найденных/ненайденных слов. Первый качественный калибровочный проход сохранён отдельно в [annotation-review.md](annotation-review.md).

Для текущей домашней работы используется [согласованный краткий отчёт](release-run/article-report.md), перенесённый в статью 15 октября 2026 года. Срез зафиксирован, фоновых запусков нет. Большие JSONL-сетки `metrics.jsonl`, `term-pairs.jsonl` и полные входы массового прогона сохраняются локально; в Git включены код, правила и отчёты. Рисунки из готовых чисел воспроизводятся по [инструкции](../../code/README.md).

## Состав и выборка

Берём **последнюю обсуждённую таблицу**, исключая AgentHop и PaSa: **ScholarQuest, Crase, PaperPilot, AutoResearchBench**. MIR и LitSearch из более раннего отбора в этот пилот не входят. Исходный LitSearch не подменяет точные задачи Crase.

План — **10 разных вопросов на набор, всего 40 вопросов**. Это число вопросов, а не пар: все опубликованные целевые статьи выбранного вопроса сохраняются, каждая образует отдельную пару для разметки. Общий объём пар указывается в manifest.json. Если ручная работа окажется слишком большой, отдельную выборку целей нужно зафиксировать до просмотра их лексической близости; сейчас цели не сокращаются.

Вопросы выбираются воспроизводимо, без сортировки по будущим метрикам или субъективной сложности: порядок по SHA256 от `seed + "|" + benchmark + "|" + source_id`, затем первые 10. Seed и хеши исходных файлов записаны в manifest.json. Для AutoResearchBench берём 5 Deep и 5 Wide. Deep без целевой статьи не образует нужной пары и не включается; количество таких исключений фиксируется. Эта небольшая выборка предназначена для настройки инструкции, а не для оценки распространённости терминологического разрыва во всём бенчмарке.

Доступность:

- ScholarQuest: публичный файл вопросов и arXiv ID целей.
- AutoResearchBench: публичный восстановленный bundle, исходные вопросы, типы задач и цели.
- PaperPilot: пилот по публичному `testcases_s2ids_clean.csv`; его соответствие каноническому тесту статьи не подтверждено. Это явно отражается в manifest.json.
- Crase: точные отфильтрованные splits и собственные 98 вопросов пока недоступны. Плановые 10 мест не заполняются вымышленными вопросами или заменой другим набором.

## Хранение

UTF-8, JSONL: одна запись на строку. Формальная схема — `records.schema.json` (JSON Schema draft 2020-12). Каждая запись имеет `record_type` и `schema_version`.

| Файл | Единица хранения |
|---|---|
| `questions.jsonl` | Оригинальный вопрос, его контекст/anchor, источник, все ID целей и исходная строка релиза |
| `papers.jsonl` | Целевая статья: идентификаторы, оригинальные title и abstract, источники и статус доступности |
| `annotations.jsonl` | Разметка одной пары конкретным аннотатором: понятия вопроса, соответствующие фрагменты статьи и виды соответствия |
| `metrics.jsonl` | Результат отдельной метрики для пары с версией алгоритма, представлением входа и параметрами предобработки |
| `annotation-review.md` | Читаемый отчёт первого калибровочного прохода: исходный вопрос, контекст, title + abstract, свидетельства и комментарии |
| `calibration-pairs.json` | Воспроизводимая выборка одной цели на вопрос для первого прохода; прочие цели остаются в пилоте |
| `query-concepts.v1.json` | Зафиксированные понятия всех 30 вопросов |
| `calibration-decisions.v1.json` | Решения LLM до вычисления смещений; источник для воспроизводимой сборки JSONL и отчёта |
| `metadata-issues.json` | Расхождения released title и названий по ID; флаги проверки, без автоматического исключения |
| `manifest.json` | Согласованный состав, способ выборки, контрольные суммы, выбранные ID и ограничения данных |
| `metric-comparison.md` | Определения, численная сетка, сравнение частей текста, контрольные и реальные примеры, рекомендация |
| `term-match-details.md` | Все оригинальные вопросы и все 593 пары с результатами и списками слов |
| `term-pairs.jsonl` | Все показатели пары и исходные найденные/ненайденные слова, без потери пропусков |
| `query-terms.v2.json` | Научные выражения, выделенные LLM только из вопросов; явные исключения хранятся отдельно |
| `metric-config.v1.json` | Версии нормализации, хеши правил и корпусов, размер окна соседства |
| `stopwords.v1.json`, `aliases.v1.json`, `idf.v1.json` | Фиксированный список служебных слов, малый словарь сокращений, веса редкости |
| `fulltexts.jsonl` | URL, форматы, хеши, доступность и ошибки получения полных текстов |
| `reference-splits.jsonl`, `reference-boundaries.v1.json` | Способ отделения библиографии и явно проверенные исключения |
| `metric-behavior-checks.json` | Диагностические проверки метрик и сохранения приложений |
| `metric-validation-summary.json` | Полнота сетки, целостность текстов, диапазоны значений и инварианты покрытия |

Исходные тексты не переписываются, не лемматизируются и не очищаются на месте. Недостающий abstract хранится как `null`, а не как пустой документ для оценки. Для PaperPilot название anchor и исходный контекст сохраняются отдельно от вопроса: выражение «this paper» нельзя молча заменить названием или игнорировать. В метрике явно указывается, использовался ли контекст.

При несовпадении названий `title` хранит название, полученное по ID, а `released_title` — исходное название из релиза. `metadata_notes` помечает необходимость проверки идентичности. Расхождение может быть сокращением названия, сменой версии или неверным ID; автоматически подменять цель статьёй с похожим названием нельзя.

`paper_id` имеет namespace (`arxiv:...`, `s2:...`). `question_id` также содержит benchmark. Общая статья хранится один раз; разметка и метрики связывают её с конкретным вопросом по ID. Исправления и независимые разметки сохраняются отдельными записями с `revision` и идентификатором аннотатора.

## Инструкция разметки v1

1. Прочитать вопрос и предусмотренный исходной задачей контекст. Выделить **ключевые научные понятия и требования**: методы, объекты, свойства, условия, ограничения, названия наборов, существенные числа. Отметить значимость: `core` или `supporting`.
2. Не размечать служебные слова и оболочку запроса: «а», «и», «в», «на», «но», «найди статьи», «во введении добавляем» и подобные фразы. Отрицания, отношения сравнения, временные и численные ограничения сохранять, если они меняют научный смысл. Слова не исключаются только потому, что они короткие или общеупотребительные: например, техническое значение `attention` требует сохранения.
3. В title и abstract выделить выражения, соответствующие каждому понятию вопроса. Одно понятие может иметь несколько фрагментов; составные и пересекающиеся понятия разрешены.
4. Указать вид соответствия: `exact`, `inflection`, `abbreviation`, `synonym`, `terminology_shift`, `descriptive`, `not_visible`, `uncertain`. `synonym` — обычное синонимическое выражение; `terminology_shift` — иное научное обозначение того же понятия, для которого можно объяснить соответствие. `not_visible` означает, что соответствие не видно в title + abstract, а не что статья нерелевантна.
5. Для составного понятия нельзя считать совпадение части подтверждением всех условий. В комментарии указывается покрытая часть, конкретизация общего понятия или непроверенное требование. `descriptive` допускает частный пример общего класса; это не автоматически эквивалентная терминология. `exact` допускает изменение регистра, `inflection` — грамматической формы.
6. Отдельно оценить научное соответствие пары по доступным текстам: `supported`, `partial`, `not_supported`, `uncertain`. Gold-статус в релизе не заменяет эту оценку. В комментарии указать, нужен ли полный текст и почему.

`confidence` означает уверенность в метке, а не вероятность релевантности. Например, можно уверенно поставить `uncertain`, если требуемого доказательства нет. `needs_full_text` означает потребность в дополнительных источниках: полном тексте, библиографии, аффилиациях или датах. `status=complete` у LLM означает завершённый проход этого аннотатора, а не человеческую валидацию. `input_sha256` фиксирует вопрос, контекст, title и abstract, к которым относятся границы и оценки.

Каждый фрагмент записывается как `text`, `start`, `end`; индексы с нуля, интервал `[start, end)`, в Unicode code points исходного поля без нормализации. Должно выполняться `original[start:end] == text`. У фрагментов статьи дополнительно поле `field`: `title` или `abstract`.

Разметка понятий вопроса задаётся **до сопоставления с целями** и должна быть одинаковой для всех его пар в одной версии инструкции. Это предотвращает подбор ключевых терминов под конкретную статью. В JSONL понятия повторяются в записи пары для удобства переноса; их ID и границы должны совпадать между парами одного вопроса и версии разметки.

Пустой список разметки не означает нулевое пересечение: до работы аннотатора записей в annotations.jsonl нет. Машинная предварительная разметка, если появится, имеет `annotation_method=llm` или `automatic` и не выдаётся за человеческую (`manual`). Общий числовой балл пересечения пока не навязывается: сначала собираются проверяемые соответствия фрагментов.

## Сравнение метрик

Метрики получают исходные тексты или размеченные понятия, не меняя эталонную разметку. В каждой записи сохраняются `metric_name`, `metric_version`, `input_view`, `preprocessing` и `score`; для IDF указывается используемый корпус, для эмбеддингов — модель и revision. Это позволяет сравнивать совпадения слов/словосочетаний, взвешенные меры и семантическую схожесть.

Служебные слова можно игнорировать при расчёте, но алгоритм выделения терминов, stoplist, лемматизация и обработка аббревиатур остаются отдельными версионируемыми настройками. Лексическое совпадение и научное соответствие — разные цели проверки.

Сетка предназначена для выбора прозрачного способа измерения на пилоте. Она не является независимым тестом согласия метрики с человеческой оценкой смысла. Для такой проверки потребуется отдельная человеческая разметка и отложенный материал. Разделять его нужно по вопросам, а при общих целевых/anchor-статьях — по связанным группам, чтобы один вопрос или статья не попадали в обе части.

## Текущее состояние

Подготовлены по 10 вопросов из трёх доступных источников; Crase ожидает точного релиза. Все **593 gold-пары / 589 уникальных статей** сохранены. Title + abstract получены для **584 статей**, у пяти S2-целей abstract остаётся `null`.

Выполнен первый калибровочный проход: **30 пар, по одной цели каждого вопроса, 146 понятий/условий**. Цель выбиралась по минимуму SHA256 от `seed|question_id|paper_id`, без отбора по похожести текстов. Разметка выполнена **LLM**, независимая человеческая проверка не проводилась. Остальные **563 пары** остаются ожидающими разметки, а не исключёнными. Рекомендация по измерению приведена в новом численном отчёте; независимый эталон терминологической эквивалентности и отложенная проверка пока не созданы.

Список понятий закреплён до основного сопоставления. Это не строго слепой эксперимент: несколько аннотаций статей ранее просматривались при проверке источников; выборка целей при этом детерминирована хешем, а не лексической близостью.

В отчёте отдельно отмечены непроверяемые по abstract условия и расхождения названий в PaperPilot. В калибровочных парах пока нет подтверждённых `terminology_shift`; обобщать этот результат на весь набор нельзя. Сравниваются 15 вариантов, включая точные слова, осторожную нормализацию, стемминг, сокращения, редкость слов, целые выражения и окна 10/30/100 слов, по семи частям текста (пять основных представлений и два диагностических). Для численного этапа используется отдельный список из 155 научных фрагментов: 149 упомянутых выражений и 6 явно исключённых тем. Он не смешивает научные термины с датами, аффилиациями и диагностическими подсказками. Вычислительная сетка охватывает все 593 пары; недоступный текст даёт `null`, а не нулевое совпадение. Числа текущего запуска и доступность текстов записаны в `metric-run.json` и основном отчёте.

Итоговый численный запуск: **83 020 записей**, 15 вариантов × 7 частей текста плюс контроль по всем содержательным словам вопроса. Полные тексты получены для **583 из 589 статей**, у всех полученных текстов отделена библиография; 6 недоступных источников перечислены в отчёте. Дополнительно удалены явно выделенные Related Work / Prior Work / Literature Review у 294 статей; в 284 таких разделов не обнаружено, у 5 PDF их границы ненадёжны и очищенный результат не выдаётся. Сравнение частей текста проводится на одинаковых **580 парах / 30 вопросах**. Полнота сетки и целостность входных файлов проверены; это не независимая проверка научного смысла.

Пересобрать представления из решений и проверить структуру, ID, смещения и хеши можно без внешних библиотек:

```sh
/usr/bin/python3 research/terminology-pilot/build_calibration.py
/usr/bin/python3 research/terminology-pilot/validate_records.py
```

Результат последней проверки — `validation-summary.json`. Научная правильность меток этой проверкой не подтверждается.


## Повторить численное сравнение

Использованы Python 3, NLTK 3.9.4, WordNet 3.0, BeautifulSoup и `pdftotext`. Точные версии и хеши входов записаны в конфигурации. Корпус WordNet берётся из официального [nltk_data](https://raw.githubusercontent.com/nltk/nltk_data/gh-pages/packages/corpora/wordnet.zip), сохраняется локально в `fulltext-cache/nltk_data/corpora/wordnet.zip`; его контрольная сумма закреплена в `metric-config.v1.json`. Расчёт не вызывает API языковых моделей.

```sh
python3 research/terminology-pilot/fetch_fulltexts.py
python3 research/terminology-pilot/measure_terms.py
python3 research/terminology-pilot/check_metric_behavior.py
python3 research/terminology-pilot/build_metric_report.py
python3 research/terminology-pilot/validate_records.py
python3 research/terminology-pilot/validate_metric_grid.py
```

Загрузчик использует публичные HTML/PDF и сохраняет исходные файлы только в игнорируемом локальном кеше. Для целей без arXiv ID разрешены явно записанные издательские/авторские источники в `fulltext-source-overrides.v1.json`. Кеш не включён в Git. Промежуточный расчёт `--partial` помечается в отчёте и не проходит финальную проверку сетки.

## Исключение Related Work и полный алгоритмический прогон — 12 октября

В основных таблицах текст с библиографией заменён текстом **без библиографии и явно выделенного Related Work**. Полный сырой текст и библиография сохранены только в диагностической сетке. Background без обзорного заголовка не удаляется; объединённый Introduction/Background and Related Work удаляется целиком и сопровождается проверкой устойчивости без таких статей. Это структурное исключение разделов, а не разметка принадлежности каждого утверждения.

- `section_text.py` — независимые от запроса правила выделения обзорных разделов.
- `related-work-splits.jsonl`, `related-work-boundaries.v1.json` — журнал, проверенные границы и явные пропуски.
- `automatic_terms.py`, `automatic-term-config.v1.json`, `automatic-term-calibration.jsonl` — выбор и фиксация чисто алгоритмического отбора именных групп; согласие с пилотным словарём не является независимой экспертной валидацией.
- `run_release_metadata.py` — разворачивает все строки тех же релизов в отдельном каталоге, получает бесплатные метаданные и сохраняет кэш для продолжения.
- `measure_release.py` — применяет зафиксированное правило ко всем 65 458 парам / 2 101 вопросу; 30 вопросов настройки отдельно помечены.
- [Массовый отчёт](release-run/report.md) показывает фактический охват, пропуски и отдельные результаты на 2 071 вопросе, не участвовавшем в настройке. Полнотекстовые показатели доступны для повторно встречающихся статей пилота и новых текстов по мере их получения. Остальные тексты не подменяются аннотациями и не считаются нулём.

```sh
python3 research/terminology-pilot/automatic_terms.py
python3 research/terminology-pilot/run_release_metadata.py --sources /private/tmp/scientific-citation-graph-agent-benchmark-audit-2026-10-11
python3 research/terminology-pilot/measure_release.py
```

Автоматический отбор использует открытый POS-теггер NLTK `averaged_perceptron_tagger_eng` из [официального nltk_data](https://github.com/nltk/nltk_data/tree/gh-pages/packages/taggers); его файлы и хеши зафиксированы в конфигурации, модель хранится локально в игнорируемом кэше. Генеративные языковые API и платные токены не используются.

### Продолжение без участия пользователя

`continue_release_run.py` продолжает текущий разрешённый прогон отдельным локальным процессом: после HTTP 429 откладывает повтор этого запроса на 30 минут, собирает статьи через доступные endpoints и пересчитывает результаты каждые 250 новых статей. Недостающие метаданные дозагружаются между такими порциями. Отчёт не объявляет полный охват, пока недостающие тексты реально не получены.

`collect_release_bodies.py` сохраняет сжатые представления без библиографии и без Related Work вместе с журналом границ. Сырые PDF/HTML используются временно и удаляются после извлечения; хеш источника сохраняется. При свободном месте менее 10 ГБ сбор останавливается с сохранением прогресса. Правила обработки зафиксированы в `release-run/runner-code-lock.json`; изменение правил останавливает продолжение при проверке перед очередным этапом, чтобы не смешивать разные версии.

Текущее состояние и PID: `release-run/driver-progress.json`, `release-run/metadata-progress.json`, `release-run/collection-progress.json`. Лог процесса — `release-run/cache/continuation.log`. Запуск не создаёт расписания или новых чатов.

```sh
python3 research/terminology-pilot/continue_release_run.py --sources research/terminology-pilot/release-run/cache --initial-delay 1800
```
